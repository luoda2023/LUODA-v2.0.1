# 根因报告：手机连 PC「连上一会儿就断」

日期：2026-09-11
现象（用户原话）：*「我用手机反连电脑端的时候，我们都在局域网（我在楼上，用的是不同的路由器），为什么访问一段时间就会断开，一两分钟有，有的时候几分钟也会断开，你不能这样断开断开。」*

主控端：手机（OPPO PFUM10 / id=905885、华为 ABR-AL80 / id=598801，报告节点上已升级到 LDesk 2.2.35）
被控端：PC `192.168.31.42` / id=466619（便携版 LDesk）

---

## 结论速览

| # | 根因 | 层面 | 状态 |
|---|---|---|---|
| A | 手机连 PC 时**根本没走局域网**，被逼到「公网地址 + 对称 NAT + 经 VPS 打洞」 | PC 端代码 | **已修复并实测通过** |
| B | 手机 Wi-Fi 在两个 AP 之间漫游/被 deauth，约 15~25 秒内整机无网（会话随之以 `os error 103` 结束） | 设备 / 路由器 | 已定位（非代码可控，见「建议」） |
| C | 掉线后的自动重连链**依赖「msgbox 是否送达 UI」**，某一条丢了就永久停摆 —— 网络恢复了也不会自己回来 | 客户端 Dart 代码 | **第一版无效，第二版（看门狗式）待复验** |

A 是「连不上 / 假连接」的根本原因，B 是「几分钟一断」的直接原因，C 是「断了就回不来、必须手动重连」的原因。三者叠加，用户看到的就是「时好时坏、连上一会儿就断」。

代码侧能覆盖的只有 A 和 C。**B 必须在设备/路由器侧处理**，否则断线本身仍会发生 —— 只是断线后的恢复不再需要人工干预。
报告另附一节记录 CI 发布链路上两处会导致「装的版本不是刚才编的版本 / 根本发不出去」的问题（签名钥匙不一致、两个工作流抢 tag）。

## 根因 A：手机连 PC 完全没走局域网

### 修复前取证（OPPO，09-11 03:44:39）

```
03:44:39.170  INFO [src/flutter.rs:1411]     Session 466619 start, use texture render: false
03:44:41.074  INFO [src/client.rs:481]       rendezvous server: rev.dicad.cn:21116
03:44:41.074  INFO [src/client.rs:545]       #1 TCP punch attempt with 47.114.75.115:443, id: 466619
03:44:41.131  INFO [src/client.rs:627]       TCP Hole Punched 466619 = 101.87.133.239:6883
03:44:41.132  INFO [src/client.rs:701]       417 ms used to TCP punch hole, relay_server: , nat_type: SYMMETRIC
03:44:41.132  INFO [src/client.rs:798]       peer address: 101.87.133.239:6883, timeout: 1000
03:44:41.132  ERROR [src/client.rs:3824]     Connection closed: Failed to make direct connection to remote desktop: Please try later(99)
```

四个关键点：

1. **对端地址是 `101.87.133.239:6883` —— PC 的公网地址**，而不是 `192.168.31.42`。手机与 PC 明明同在 `192.168.31.0/24`。
2. `nat_type: SYMMETRIC` —— 因为手机经 WebSocket 注册到 hbbs，`nginx` 转发后源端口丢失被写死成 0，同网段快路径 `same_intranet` 判定失败，反而被 `peer_is_lan ^ is_lan` 改判成对称 NAT。
3. `#1 TCP punch attempt with 47.114.75.115:443` —— 打洞**要经 VPS**，正是用户明确不要的路径。
4. `relay_server: ` 为空 → 连中继回落都没有，打洞失败即硬失败（`client.rs:879 bail!`）。
5. 全过程**没有一行** `Direct connection to 466619, candidates: ...` —— 说明局域网候选集为空，手机压根没找到 PC。

### 为什么找不到 PC

PC 当时跑的是**未修复版**的便携运行时（`%LOCALAPPDATA%\LDesk\runtime\4ddab2b26e0ba6a98aab2197e3b6f270\luoda.dll.bak-before-lanfix`）。该版本的 `src/rendezvous_mediator.rs` 用

```rust
let start_lan_listening = crate::platform::is_installed();
```

作为局域网发现监听（UDP 21119）的闸门。`is_installed()` 在 Windows 上查的是注册表 `InstallLocation` 指向的 `LDesk.exe` 是否存在，便携运行时两条路径都不存在 → **永远不绑定 21119**。

实测（修复前）：PC 进程只有 `TCP 21118`，**没有 UDP 21119**；向 `192.168.31.42:21119` 发 ping **无应答**。
手机侧所以只能拿信令服务器给的公网地址，走对称 NAT 打洞 —— 必然失败。

### 修复

`2b04ccf`（上一轮已提交并部署）：便携 / 免安装运行时同样启动局域网发现监听，另加单播网段扫描兜底。

也就是说：**根因 A 修好之后，「连上一会儿就断」中的「连上」已解决且稳定**；仍有断，来自根因 B / C。

## 根因 B：手机 Wi-Fi 漫游 / 被踢，整机断网 15~25 秒

### 客户端日志（华为，09-11 06:08:25）

```
06:02:08.203  INFO   Session 466619 start …（局域网直连建立，正常投屏）
06:08:25.944  ERROR  [src/client.rs:3824]  Connection closed: Software caused connection abort (os error 103)(103)
06:08:25.943  ERROR  [websocket.rs:275]    IO error: Software caused connection abort (os error 103)
06:08:25.960  ERROR  [rendezvous_mediator.rs:137]  rendezvous mediator error: Network is unreachable (os error 101)
06:08:26.016  WARN   [websocket.rs:129]    … failed to lookup address information: No address associated with hostname
06:08:43                                  网络自行恢复（TLS 校验报错重新出现 = 真连通）
```

要点：

* 数据通道（局域网直连 TCP）与信令通道（到 `rev.dicad.cn` 的 WSS）**在同一毫秒一起断**，两边都是 `os error 103`（ECONNABORTED，本机侧中止），**不是对端 reset（那会是 104）**。
* 紧接着 `Network is unreachable (os error 101)`，再接着 **DNS 全部解析失败**。
* 约 18 秒后自行恢复。

### 手机 Wi-Fi 状态机（同一台机器）

```
rec[9] : 09-11 04:00:06.881  NETWORK_DISCONNECTION_EVENT  ssid:683EFAF37D  bssid:d4:da:**:**:b8:bd  reasonCode:3
rec[58]: 09-11 06:08:26.028  NETWORK_DISCONNECTION_EVENT  ssid:683EFAF37D  bssid:d4:da:**:**:b8:bd  reasonCode:6
rec[16]: 09-11 04:01:58.723  ASSOCIATING  bssid:d4:da:**:**:b8:be      ← 另一个 AP
rec[35]: 09-11 04:01:59.393  rssi=-48  f=2457   ← 切到了 2.4G，之前是 f=5240 rssi=-65（5G）
rec[54]: 09-11 04:02:37.202  COMPLETED    bssid:d4:da:**:**:b8:bd      ← 又切回来
```

**`06:08:26.028` 的 Wi-Fi 掉线事件与会话死亡时刻 `06:08:25.944` 完全重合。**

`…b8:bd` 与 `…b8:be` 是**两个不同的 AP**（就是用户说的「两台路由器」）。手机在两者之间反复漫游 / 被 deauth，每次都要重新关联、重新拿地址、重建路由，期间所有 TCP 连接一起作废。这正是「一两分钟有，有的时候几分钟也断」的来源 —— 断的间隔取决于什么时候发生一次漫游。

### 建议（设备 / 路由器侧，代码改不了）

1. 两个路由器**不要用同名 SSID**，或把其中一个改成只发 5G；让手机固定连信号好的那台。
2. 若能开 802.11k/v/r 快速漫游就开；否则关掉其中一台的 Wi-Fi，避免手机来回切。
3. 手机侧把 LDesk 加入「电池优化白名单 + 允许后台活动 + 允许自启动」。
   **实测两台都已豁免**：华为 `dumpsys deviceidle whitelist` 含 `com.luoda.remote`；
   OPPO `am get-standby-bucket com.luoda.remote` = `10`（EXEMPTED）。这一项不是本次问题的原因，无需再动。

代码侧能做的加固（见根因 C）是：**网络一恢复就自动把会话接回来**，把 15~25 秒的断网从「对话结束」降级成「画面卡一下」。

## 根因 C：自动重连链依赖「msgbox 送达 UI」，某一条丢了就永久停摆

这一条是本报告里**返工过一次**的结论。第一版修复（`f1714c6` / 2.2.35）把原因判成
「失败文案没进重试关键字名单」，加完关键字、放宽窗口后**实测仍然不重连**。
第二版（`4942488` / 2.2.36）才找到真正的结构性缺口，并换成看门狗。下面按时间顺序如实记录。

### 取证一：第一版假设（失败文案不在名单里）

```
06:08:26.950  INFO   Direct connection to 466619, candidates: […], kind: lan, timeout: 1500   ← 自动重连第 1 次（退避 1s）
06:08:26.960  ERROR  Connection closed: Failed to connect directly to 466619 using 192.168.31.42:21118, …: Please try later(101)
```

这一次重连落在断网窗口里必然失败，且失败文案不在此前的重试名单里，于是 `hasRetry = false`，
`showMsgBox` 走 else 分支把结果标志位清空 —— 整条链终止。

### 取证二：第一版修复后仍失败（决定性）

2.2.35 部署到 OPPO（`versionName=2.2.35 / versionCode=2950`，原地升级、配置保留）后，
用 `wifi_cut_test.py 7358bbbb 20 200` 制造一次「Wi-Fi 断 20 秒」，完整时间线：

```
07:34:30.455  Session 466619 start                              ← 局域网直连建立
07:34:30.459  Direct connection to 466619, kind: lan            ← ✅ 走的是 192.168.31.42:21118
07:35:12.643  websocket IO error: os error 103                  ← Wi-Fi 被拔
07:35:12.643  Connection closed: os error 103(103)              ← 第 1 次失败 → 命中 linkLost
07:35:13.656  Direct connection to 466619, kind: lan            ← 自动重连第 1 次（退避 1s）
07:35:15.186  LAN direct connection to 466619 failed (…:21128), falling back to signalling   ← 本次新加的 Rust 修复生效
07:35:15.223  Connection closed: failed to lookup address information: No address associated with hostname(2)
                                                                ← 第 2 次失败，文案也命中 linkLost
07:35:16.8    第 3 次重连（退避 2s）
07:35:46.876  start rendezvous mediator of rev.dicad.cn          ← DNS 已恢复，信令自愈
             ……此后 96 秒日志静默，没有任何 Session 重建
```

关键对照：**同一时刻信令侧的 `rendezvous_mediator` 自己重连循环恢复了（07:35:46），
而会话侧永久停摆。** 也就是说这不是「关键字没匹配上」，而是会话重连链**根本没被再次驱动**。

### 代码原因（真正的）

`flutter/lib/models/model.dart`：重连的推进完全挂在「`Connection Error` 这条 msgbox
有没有被 `handleMsgBox` 处理」上 —— 只有走到 `showMsgBox()` 才会装 `_timer` 并让
`_reconnects *= 2` 继续退避。任何一次失败的 msgbox 丢失/未被处理，链就断在半路：

```dart
// 旧实现：唯一的推进点
_timer = Timer(Duration(seconds: _reconnects), () => reconnect(...));
_reconnects *= 2;
```

而这条路径的每一环都建立在「上一条事件已经送达」之上：`reconnect()` 里
`dialogManager.dismissAll()` + `showLoading()` 会重建覆盖层，`msgBox()` 又调
`dialogManager.dismissAll()`；一旦某轮事件时序错位，退避链就静默停摆。

### 修复（`4942488` / 2.2.36）

把重连从「事件驱动」改成「**看门狗驱动**」——判据只有一个：会话是否已被判定为链路抖动掉线。

```dart
Timer? _linkLostWatchdog;        // 每 1 秒醒一次
bool   _linkLostReconnecting;    // 是否处于自愈中
int    _linkLostDelay;           // 退避：1/2/4/8/16/30/30…
DateTime? _linkLostStart;        // 总窗口 300s
```

* `isLinkLostError(title, text)` 判定本机链路抖动：`connection abort` / `error 103` /
  `unreachable` / `error 101` / `no address associated with hostname` /
  `lookup address information` / `failed to connect directly` / `failed to connect to ` /
  `failed to connect via` / `please try later`；
* 命中即 `startLinkLostWatchdog()`，看门狗**不读取任何后续事件**，按 1/2/4/8/16/30… 秒
  退避反复调 `sessionReconnect`，直到连上或超出 300 秒总窗口；
* 三个收敛点负责收掉它：`connection_ready`（连上）、`waiting-for-image`（对端认下会话）、
  `close`（会话被真正关闭）；
* 链路抖动期间 **msgbox 的一次性定时器不再并跑**，避免两条链互相 `cancel` 掉对方刚发起的重连。

Rust 侧未动：`session_reconnect` 在 `ConnectionState::Connecting` 时会直接 return，
所以看门狗按 1 秒节拍密集调用是幂等、安全的。

### 效果与用户视角

一次 Wi-Fi 漫游 ⇒ 掉线后最多几十秒自动接回局域网直连，**不需要用户任何操作**；
若手机彻底离线，最多自愈 5 分钟后停手，把界面交还给用户。

## 附带修复：局域网候选失败不再掐断信令链路

`src/client.rs` 的 `_start()` 里，原本只要 `hosts` 非空且全部连不上就 `bail!`：

```rust
Err(e) => bail!("Failed to connect directly to {} using {}: {}", peer, hosts.join(", "), e),
```

这等于**把信令 / 打洞链路也一起掐死**。而局域网友好候选是从 `config::LanPeers` 缓存读出来的，**从没在当前这轮校验过** —— 对端换过 IP / 换过网卡时，一条过期记录就能让连接彻底失败，且失败原因还是笼统的「直连失败」。

改成：

1. 这批候选若来自缓存，先补一轮现场发现（广播 + 单播）再重试一次；
2. 仍失败则**回落信令 / 打洞链路**（不再 `bail!`），让上层拿到真正的失败原因（例如对端经 WebSocket 注册后端口为 0 时给出的可操作提示）。

IP / IP:port 字面量语义不变：调用方点名要连这个地址，失败就是失败。

### 复验方法（部署 2.2.36 后执行）

不用真去楼上走一趟，直接用 adb 精确制造一次「Wi-Fi 掉 20 秒」：


## 根因 C 的第二半：**对端**进程重启（`os error 104`），2.2.36 仍回不来

上面三组实验断的都是**手机自己的 Wi-Fi**（Rust 侧报 `os error 103` = 本机侧中止）。

### 代码原因（两处，都在同一个判断里）

1. `isLinkLostError()` 的名单是照着**本机链路抖动**写的
   （`connection abort` / `error 103` / `unreachable` / `error 101` / DNS / 直连失败 / `please try later`），
   **`connection reset` / `error 104` 是对端侧原因，不在名单里**；
2. `shouldAutoRetryOnOffline()` 虽然认得这两个词，但它的窗口只有 **30 秒**，
   而「对端重启 → 重新注册 → 重新监听 21118」实测要 **60~90 秒**，30 秒**刚好够不着**；
   更早的毛病是它的推进也挂在 msgbox 上（第二层已述）。

### 修复（`85449c7` / 2.2.37）

不新开一条链，而是让**所有值得重连的 `Connection Error` 都走同一个看门狗**，按原因给窗口：

```dart
startLinkLostWatchdog(String reason, [int? windowSeconds])

// handleMsgBox 的 else 分支
final linkLost = isLinkLostError(title, text);
if (!hasRetry) { hasRetry = linkLost || shouldAutoRetryOnOffline(type, title, text); }
if (hasRetry && title == 'Connection Error') {
  startLinkLostWatchdog(text,
      linkLost ? _kLinkLostMaxWindowSeconds      // 300s：本机链路抖动，等 Wi-Fi 漫游回来
               : _kPeerOfflineMaxWindowSeconds); // 120s：对端侧，覆盖对端重启的 60~90s
}
```

三个容易写错的点：

* 看门狗**已在跑时只放宽窗口、不缩短、也不重置退避** —— 退避必须跨多条 msgbox 连续累积，
  一重置就永远卡在 1 秒重试；
* `msgBox` 的 `reconnectTimeout`（按钮上的倒计时）改成显示看门狗的**真实退避** `_linkLostDelay`；
  旧代码读的是早已停摆的 `_reconnects`，界面上永远显示 1 秒，会把人带偏；
* `stopLinkLostWatchdog()` 里必须把 `_linkLostWindow` 复位，否则下一轮会继承上一轮的窗口。

### 根因 D：104 场景发的是 `relay-hint`，**绕过了**看门狗

`src/client.rs:3889 on_establish_connection_error`：

```rust

    && ((cfg!(windows) && (errno == 10054 || err.contains("10054")))
```

## 根因 E：`websocket` 一票否决了 hbbs 的「同内网」判定（2.2.38 修）

这一条不直接表现为断线，但它决定了**能不能拿到局域网直连**——而直连拿不到，
后面所有"连上一会儿就断"的观感都会被放大。

hbbs 的 `handle_punch_hole_request` 判定两端同内网的表达式是：

```rust
let same_intranet = !ws && (peer_is_lan && is_lan || a.ip() == b.ip());
```

注意开头那个 `!ws`。客户端侧 `should_start_with_tcp` 在 `websocket == true` 时
**强制**先走 TCP/WSS 注册，于是 `ws` 为真 → `same_intranet` 恒为 `false`
→ 两端被判为 `SYMMETRIC`，只能打洞，**永远拿不到 `is_lan` 那条捷径**。

实测三端（PC `192.168.31.42`、OPPO `192.168.31.70`、华为 `192.168.31.243`）
**同一网段同一 SSID**，本该秒判同内网。修法：

```rust
// src/rendezvous_transport.rs
let _ = websocket;              // websocket 不再强制先走 TCP/WSS 注册
test_tcp || proxy || udp_disabled
```

历史成因（注释里已写明）：移动端运营商常封 21116-21119，所以当年被改成
"移动端优先 WSS(443) 注册"。但在**局域网内**这台手机并不需要绕封禁，
反而因此丢掉了同内网直连。测试同步更新：
`websocket_does_not_force_tcp_registration`（含 `proxy=true` 仍强制 TCP、
`udp_disabled=true` 仍强制 TCP 两条边界）。

**明确不做的两件事**（都试过或推演过，做了更糟）：

| 想法 | 结论 |
|---|---|
| 给 hbbs 加 `--mask` | **不做**。`--mask` 会把 `is_lan` 置真，在 `!ws && peer_is_lan && is_lan` 里等于**主动强制** `same_intranet`，跨网段的真实场景会被误判成同内网，比不加更糟 |
| 继续让移动端优先 WSS 注册 | **不做**。局域网内没有封禁问题，代价是同内网判定被一票否决 |


## 补强：额外网段单播扫描 `lan-sweep-subnets`（2.2.38 新增，默认关闭）

`unicast_sweep_plan()` 原先只扫**本机每个私有网卡所在的 /24**（收敛规则见
`SWEEP_HOST_LIMIT`）。这覆盖不了「两台设备挂在不同路由器后面、不共享二层广播域，
但上联设备互相可达」——广播出不了路由器，而对端网段的**单播**能到。

新增本地配置项：

```toml
# 本地配置（LocalConfig），留空 = 完全不产生额外流量，行为与改前一致
lan-sweep-subnets = "192.168.1.0/24,10.0.0.0/16"
```

- 解析 `parse_sweep_subnets`：逗号 / 分号 / 空白分隔，**跳过非法项只 warn**（手写配置项，一个错字不该让整个局域网发现失效）
- 前缀收敛到 `[8,30]`，每网段上限 `SWEEP_HOST_LIMIT`(254)，网段数上限 `EXTRA_SWEEP_SUBNET_LIMIT`(8)
- 与本机网卡已覆盖的网段自动去重
- 绑定 `0.0.0.0` 发送，交给路由表选出口（跨网段本来就该这样）
- 测试：`lan.rs` 新增 `sweep_subnets_parses_common_forms` / `sweep_subnets_skips_garbage_without_losing_the_rest` / `sweep_subnets_empty_by_default_and_capped` / `sweep_targets_are_bounded_and_exclude_network_and_broadcast` / `extra_sweep_subnets_is_bounded`

**它解决不了的**：真·双 NAT（两端各自在运营商级 NAT 后、互相不可路由）。
那种情况只有 ① 打洞成功走 P2P，或 ② 走中继。这一项只是把"路由可达但广播不可达"
这条最常见的中间地带补上。

## 附：CI 发布链路（两处会导致发布失败/装不上）

### 1. APK 签名与手机上已装的 APK 不一致

| | SHA-256 | DN |
|---|---|---|
| 两台手机已装 APK（= 仓库内 `flutter/android/app/luoda-release.keystore`） | `786974b1…` | `CN=LUODA,OU=LUODA,O=LUODA,L=Beijing` |
| CI 出的 APK（= Actions secrets 里那把） | `337e3690…` | `OU=Mobile,O=LUODA,CN=LUODA Android Release` |

两把钥匙不同 ⇒ `adb install -r` 直接 `INSTALL_FAILED_UPDATE_INCOMPATIBLE: signatures do not match`，
应用内更新同理，用户只能卸载重装（配置全丢）。9/11 凌晨是靠**用本机 keystore 对 CI 包重新签名**
（`zipalign -c` → `apksigner sign`）才装上 2.2.35 的。

**根治**：`build-apk.yml` 的签名步骤改为**优先使用仓库内的 `luoda-release.keystore`
+ `key.properties`**（这两份文件本来就被 git 跟踪、已公开），Actions secrets 降级为
「仓库内 keystore 缺失时才用」的回落，不再硬校验 secrets 是否存在。
这样 CI 产物可以直接原地升级。

### 2. 两个工作流并行发版抢同一个 tag

APK 与 EXE 两个工作流都会给 `v<版本号>` 建 Release，谁先跑完谁建成。
原来两边都用 `softprops/action-gh-release@v1`，**后来者遇到 tag/release 已存在会直接抛
`already_exists` 失败**。v2.2.33 与 v2.2.35 的 EXE 都是这样挂掉的：

```
Build LDesk Windows EXE  run 34537462406
  …20 步全部 success（含 Build Flutter Windows / Sign / Packer / Upload artifact）
  FAIL 22 Upload to Release (nightly x64 only)     ← 唯一失败步骤
⇒ Release v2.2.35 里只有 4 个 APK，没有 LDesk-portable-x64.exe
```

**修复**：两个工作流都改成 `gh release view || gh release create` + `gh release upload --clobber`，
幂等、可重跑、与先后顺序无关。

即 `rev.dicad.cn:443` 出的是 `CN=dicad.cn`（SAN 仅 dicad.cn）的证书，与 SNI 不匹配，手机每次都先失败再降级「接受无效证书」。这条不影响本次修复的局域网直连路径，但会让信令链路每次都多一次往返、并依赖降级逻辑。

**已核实的条件（补齐）**：

* 1Panel `agent.db` 的 `website_ssls` 表里 **id=6 就是 `rev.dicad.cn`**：`status=ready`、`auto_renew=1`、
  `provider=http`、`expire 2026-12-09`（用户在 9/10 19:03 申请的就是这张）。CN/SAN 均为 `rev.dicad.cn`，与私钥配对校验通过。
* 但 1Panel 的 `websites` 表里**没有 rev.dicad.cn 站点**，所以证书文件从未落到 `/opt/1panel/www/sites/rev.dicad.cn/ssl/`。

**修改方案已预置完毕（未生效，零风险）**，全部产物在 VPS `/root/luoda-vps-certfix/`：

| 文件 | 作用 |
|---|---|
| `ssl/fullchain.pem` `ssl/privkey.pem` | 从 `agent.db` 导出的 id=6 证书物料（配对已校验） |
| `rev.dicad.cn.conf` | **整块复制** `dicad.cn.conf`，只改 `server_name` 与 `ssl_certificate*` 两处 |
| `apply.sh` | 备份 → 装证书 → 装新块 → 从 `dicad.cn.conf` 摘掉 `rev.dicad.cn` → `nginx -t`（失败自动回滚）→ reload |
| `revert.sh` | 一键回滚到最近一次备份 |
| `sync-cert.sh` | 幂等兜底：读 DB 比 SHA256 指纹，变了才写盘 + reload（防「裸证续期不写盘」） |

之所以做成「整块复制」而不是新写一份精简配置：新写容易漏 location，而 `dicad.cn` 这个块承载
**全部客户端的信令（`/ws/id` `/ws/relay`）、管理面板（`/_admin/`）、API（`/api/`）与 Web 端（`/_web/`）**，
漏一条就是全站事故。**该变更需用户确认后再执行**（`bash /root/luoda-vps-certfix/apply.sh`）。

### 附带发现 1：PC 侧凌晨 04:00 也会整机断网一次

### 附带发现 2：`.github/workflows/renew-server-cert.yml` 已失效

该工作流假设宿主机上有 nginx，实际本机 OpenResty 跑在 Docker 里：

* `certbot renew --nginx` / `certbot certonly --nginx` —— 宿主机没有 nginx，插件无法工作；
  现存 certbot 证书（`/etc/letsencrypt/archive/rev.dicad.cn/`）的 renewal conf 记的是 `authenticator = webroot`，
  即历史上是靠 webroot 签出来的，与工作流里的 `--nginx` 不一致；
* `systemctl reload nginx` —— 宿主机无该服务（load 的是容器内 openresty）；
* 它写入的 `0 3 * * * certbot renew …` 在 VPS 的 crontab 里**并不存在**（实际靠 `certbot.timer`）。

建议改为：走 1Panel 的证书续期（HTTPS 申请时选 HTTP-01，服务端 `/opt/1panel/www/` 已挂进容器），
把「续期 → 部署到容器 → reload」交给 1Panel，或至少把工作流里的 `--nginx` 换成
`--webroot -w /opt/1panel/apps/openresty/openresty/root` 并去掉 `systemctl reload nginx`。
